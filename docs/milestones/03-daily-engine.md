## What we built and why

M3 builds the daily loop of ADR-0001 §1 and everything it calls. One class (`Run`, `src/volbt/engine/loop.py`) holds the state of a run and runs eleven steps per session, in a fixed order: load the session, book the start-of-day events, fill yesterday's orders, settle the contracts that expire, mark every lot, hedge, take the snapshot, check ruin, let the strategy decide, decide early exercise, write. The pieces are the fill model of ADR-0002 (integer-cent prices, quote states, the volume cap, whole packages), settlement and early exercise as bookings (ADR-0003), one mark per lot with NAV_mid and NAV_liq (ADR-0004), the delta hedge (ADR-0005), and interest, dividends and the borrow fee as cash flows in integer cents (ADR-0005 §6, ADR-0007 §2). The run writes a ledger of 12 parquet tables whose bytes depend only on the inputs, the config, the commit and the code (ADR-0001 §7 and amendment 11). A year cache sits behind the look-ahead guard so that a 14-year run takes seconds, not minutes. A reference strategy, `RollingShortStraddle`, sells 10 at-the-money straddles on the standard monthly expiry nearest 30 days and closes them 7 days before expiry; it exists so that every part of the engine runs on real data before M4 builds the real structures. The app gains a Blotter tab and a Positions tab, fed by two new datasets, `blotter.json` and `positions_timeline.json`, from the development run.

What a user can now do: run `tools/run_backtest.py` on any sample the split protocol allows and get a ledger; read its health with `tools/report_m3.py`; and open the app's Blotter and Positions tabs. The first two commands print no P&L, by design (decision D19).

The milestone also fixed what it found. The tests showed one engine bug (shares delivered by an *early* assignment were never liquidated when the book was unhedged; "Pitfalls", row 6). The mutation run found three test gaps (mutants 35, 37, 40) and a fourth survivor, on the cache's private reader (mutant 38, equivalent for every public caller); `tests/test_engine_provenance.py` closes all four. The engine's own edits to `src/volbt/data/store.py` and `src/volbt/view.py` changed the pricing build's code fingerprint, so the whole store was re-priced; the 66 parquet files came out byte-identical to M2's.

Then one adversarial review attacked 11 claims (Opus, 2026-10-30; the findings are labelled R1 to R10 in the ledger). It found, and the fixes made: a `same_close` NAV that counted the lots closed at the close twice (R1); a run stopped early that took the full run's id and replaced its folder (R2); a run id that named a `-dirty` commit and so no code (R3); a map entry, 2018-12-05, resting on a notice that does not name SPY (R4; restored in round 2, when OCC memo #44125 was read); a crash for any expiry after the calendar's last session (R5); surface fills that carried no flags, against ADR-0002 §7 (R6); six mutants that no behaviour test killed (four survived the whole suite; two, in `h_model`, failed only notebook tests that compare copied source text), now killed by `tests/test_engine_review.py` (R7); an app parser that accepted a long lot "assigned" (R8); and three documentation errors (R9). It also found three smaller points that are documented and not fixed (R10), and two contradictions that the app still accepts (R8). The ledger has the evidence, the fix and the test for each.

A second round (2026-11-09: a verifier, a design and documentation reviewer, and a code reviewer, both Opus) found more, and the fix pass of 2026-11-09 fixed it: a strategy could read future smile rows through the zero-copy frames the year cache returned (CR-1); the expiry picker took Wednesday weeklies for monthlies when the third Friday was unlisted (DS-NEW1); the engine did not enforce the 180-day cap (CR-7) or the strategy's exit reasons, so the exporter could write a file the app refuses (DS-6); three behaviours no test pinned (the close fee, the sub-cent surface sale, `next_open` hedges; CR-9); app parsers that accepted contradictions a file can prove (DS-6, CR-10); the 2018-12-05 entry, whose OCC memo the round-2 reviewer read (DS-1); a stopped run whose id named a weekend (CR-a); and documentation errors. The ledger's "Round 2" lists each finding, its severity, the fix and the test that fails without it.

## Data flow

One position, followed from its order to its close: position 63 of the development run, 10 short SPY 2015-04-17 205 straddles. Its values were read back from the ledger [report, block "trace"; the ledger tables and the committed JSON].

1. **The order** (Friday 2015-03-13, step 9). The book was flat: the previous position had closed at that day's close. `RollingShortStraddle.decide` (`reference.py:48`) called `entry_order` (`:66`): of the standard monthly expiries, 2015-03-20 has 7 days (under the minimum of 21) and 2015-05-15 has 63, so `nearest_monthly` picked 2015-04-17, 35 days out, and the listed strike nearest that expiry's parity forward, 205. The intent was a short straddle of 10 packages. `check_intent` (`loop.py:586`) found both contracts in the snapshot, and `new_order` (`:574`) made order 125 with target date 2015-03-16, the next session. Each leg got V_t = null (OptionsDX volume is null in 2015) stamped with the date 2015-03-13. Position 63 was created with status `pending`.
2. **The fill** (Monday 2015-03-16, step 3). `fill_pass` (`loop.py:431`) read the 03-16 quotes through that day's view: call 5.21 / 5.24, put 2.51 / 2.54. Both are valid and pass the opening filter (a bid of at least 5 cents, a spread under 25% of the mid). At k = 1 a sale gets the bid: (4 × 1,045 − 4 × 3) // 8 = **521** cents, and for the put 251. The cap was the hard cap of 100, so all 10 packages filled. Fees were 10 × 70 cents = **$7.00** a leg. The cash flows of the day, in the order they were booked: interest 250 cents (step 2), `option_premium` +521,000 and +251,000 cents with `option_fee` −700 cents each (step 3), then the hedge (step 6). Position 63 became `open`.
3. **The mark** (step 5, same day). Both lots were `QUOTE_MID`: 5.225 and 2.525. Both took mark IV 0.1524: the put is out of the money and uses its own IV, and the call, in the money, takes the surface IV at its strike (flag 64, `GREEKS_OTM_IV`). Delta was −619.3 shares for the short calls and +376.4 for the short puts; vega −234 USD per vol point for each lot.
4. **The hedge** (step 6, same day). Net delta was −242.97 shares, so `hedge_shares` bought **243** at the close of 208.58, leaving 0.03. The cost was a commission of 243 × $0.005 = $1.215 (above the $1.00 minimum) and slippage of $1.215, each rounded half up to 122 cents: **$2.44**. The share trade was −5,068,494 cents.
5. **The nights** (steps 2 to 11, 18 sessions from 03-16 to 04-09). Every session marked both lots from the quote mid (36 `QUOTE_MID` rows in all) and hedged: on 03-17 the delta was +50.83 and the hedge sold 51 (cost $1.26); on 03-27 it bought 53 ($1.27); on 04-09 it bought 176 ($1.88). Step 10 ran each night; the ledger holds no early event for this position, so both lots stayed until the close order.
6. **The close order** (Thursday 2015-04-09, step 9). The next session is Friday 04-10, and 04-17 is 7 days later, which is the strategy's `exit_dte` of 7. `exit_order` (`:56`) made a close for 10 packages (the gcd of 10 and 10) with ratio +1 per leg and reason `dte`: order 126, target 2015-04-10.
7. **The close fills** (04-10, step 3). A reduce-only order gets the hard cap of 100 only. The call was quoted 5.07 / 5.20 and the put 0.12 / 0.13; a buy at k = 1 pays the ask: **5.20** and **0.13**. Fees were $7.00 a leg. `close_lot` (`loop.py:248`) set both lots to quantity 0 and the position to `closed` with exit reason `dte`. - **The import-boundary rule is a tripwire, not a sandbox** (round 3, claims 1 and 2). It catches accidents; a strategy written to read memory by address can still read past the end of an array, and nothing in M3 isolates strategy code (ADR-0001 test 1, `YearCache`'s docstring).
- **What the app's parsers cannot check.** Since round 2 they check what a file can prove (ADR-0001 amendment 15), the open counts and a relabelled close included. They cannot check what a file does not carry: that a fill's price was its day's quote, or any cash amount. The Python audit (`tests/test_engine_audit.py`) checks those on the ledger.
- **`on_session_end` hands the live `Book` to its caller** (finding R10). It is a test hook and is not part of the run id, so a hook that changed the book would change the ledger without changing the id. Only tests pass one (`tests/test_engine_provenance.py:71`, `tests/test_engine_loop.py:311`); nothing in `src/` or `tools/` does.
- **The cash identity proves only that cash moves through `Run.flow`** (finding R10): `cash = initial + sum(flows)` can fail only if a cash change bypasses it, so it says nothing about the amounts. Since round 2 `tests/test_engine_audit.py` recomputes every flow, fill price, share count, mark and NAV from the store and the ADRs, importing nothing from `volbt`: on the made-up fixture under six configurations, and on the recorded development run under `real_data`. The interest, dividend and fee tests of `tests/test_engine_cash.py` pin the formulas (mutants 20a to 20c and 32).
- **`check_ledger` guards against accidents, not tampering** (round 2, CR-b). The hashes it checks are read from `run_meta.json` in the same folder, so a table edited together with its hash passes; nothing signs the files (its docstring; ADR-0001 amendment 14).
- **The 60-second budget on other hardware.** One machine, loaded and unloaded, is what was measured.
