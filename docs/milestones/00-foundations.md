## 1. What milestone 0 built, and why this design over the alternatives

Milestone 0 contains no market data and no strategy. It builds the things every later milestone leans on: a reproducible toolchain, a one-way contract between Python and the browser, one honest placeholder picture, and ten written decisions.

### 1.1 The scaffold

- **Python 3.12 and uv, with exact pins.** `requires-python = "==3.12.*"` (`pyproject.toml:5`), `.python-version` says `3.12`, every dependency is `==` pinned (`pyproject.toml:6-14` and `17-20`), and `uv.lock` records the whole resolution. The reason is ADR-0001 §7: a backtest that must reproduce byte for byte cannot sit on a numpy or pandas that changed under it. The app does the same: `app/.npmrc:1` sets `save-exact=true`, `app/package.json` has no `^` or `~`, and it records the Node it was tested on: `"engines": {"node": ">=22 <23"}` (`app/package.json:7`) and `app/.nvmrc` containing `22`. The Mermaid renderer is pinned the same way (§2.2).
  - *Rejected:* version ranges (a transitive upgrade silently changes numerics), bare `pip` + `requirements.txt` (does not lock transitive dependencies), conda or poetry (heavier, no gain here).
- **A `src/` layout.** The package is `src/volbt/`, not `./volbt/`. With a flat layout, `import volbt` works from the repo root only because the current directory is on `sys.path`, so tests can pass against the source tree while the installed package is broken. With `src/`, the package is importable only through an install or an explicit path, so the tests use the same import path a user gets.
- **An editable install through the `uv_build` backend.** `[build-system]` pins `uv_build==0.11.25` (`pyproject.toml:28-30`) and names the module (`pyproject.toml:32-33`). `uv sync` therefore installs `volbt` into `.venv` in editable mode, and `uv run python -c "import volbt"` works (it prints the path `src/volbt/__init__.py`; checked this session). Pytest has a second route in `pythonpath = ["src"]` (`pyproject.toml:22-24`), which still works in a checkout that has not been installed. The two scripts in `tools/` used to prepend `src/` to `sys.path` under a comment saying `volbt` is not installed. Once the editable install existed that was dead code, and the test that claimed to run the exporter "with volbt NOT on the path" could not fail, because `volbt` was importable either way. Both hacks are gone: the scripts import `volbt` plainly (`tools/export_app_data.py:20`, `tools/build_notebooks.py:35`) and derive their repo paths from `__file__`. Three tests now check something that can fail (`tests/test_export.py:194-230`): the first runs `python -I` (isolated mode, which ignores `PYTHONPATH` and the current directory) from another directory and requires `volbt` to resolve to `src/volbt/__init__.py`; the second runs the exporter as a plain script from an unrelated working directory; the third loads the script from a foreign directory and checks that its default output folder is still the repo's `app/public/data`, so it never depends on where it was started.
- **Layout.** `src/volbt/` (library: `config`, `contract`, `illustrative`), `tests/`, `tools/` (notebook builder, exporter, Blender script, Mermaid renderer), `notebooks/` (generated), `app/` (Vite + React 19 + TypeScript + three.js), `docs/` (ADRs, diagrams, concept notes, milestone walkthroughs). Raw vendor data is *outside* the repo (`src/volbt/config.py:1-11`, `.gitignore:8-12`). `.gitattributes` pins `*.ipynb`, `*.json`, `*.py`, `*.svg`, `*.mmd`, `*.md`, `*.ts`, `*.tsx` and `*.sh` to LF line endings and `*.png` to binary, because the notebook check and the exporter's drift test compare bytes (a Windows checkout that turned LF into CRLF would otherwise report drift; round 2 found `*.svg` and the other generated or committed text files unpinned). A test asks `git check-attr` rather than reading the file (`tests/test_notebooks.py:364-386`).

### 1.2 The notebook builder and its sync test

`notebooks/00_scaffold_tour.ipynb` is not written by hand. `tools/build_notebooks.py` builds it by *copying code out of* `src/volbt/illustrative.py`, and the sync test (`tests/test_notebooks.py:20-28`) fails if the committed file differs from a fresh build. It compares **bytes**: `read_text()` turns CRLF into LF, so a CRLF notebook used to pass the test while `--check` reported drift. That gives one source of truth: `src/` is what the tests run, and the notebook can never drift from it.

It is **byte-deterministic** on purpose, so that a rebuild shows up as a git diff only when something real changed (and so the `--check` comparison can settle). §2.2 lists the ingredients.

- *Rejected:* hand-maintained notebooks (drift), executed notebooks with stored outputs (timestamps, kernel versions and execution counts make every save a diff), a notebook that only does `import volbt` (readers on GitHub then cannot see the code), and `jupytext` (one more moving part).

### 1.3 The Python-to-app JSON contract, and why the app never computes results

The only thing that crosses from Python to the browser is a set of JSON files in `app/public/data/`. Every file starts with the same envelope (ADR-0001 §5):

| Field | Meaning | Written at | Validated at |
|---|---|---|---|
| `schema_version` | `MAJOR.MINOR.PATCH` of the file layout | `src/volbt/contract.py:24` | `app/src/lib/contract.ts:87-96` |
| `generated_at` | UTC time written, ISO-8601 with `Z` | `src/volbt/contract.py:132` | `app/src/lib/contract.ts:100-124` |
| `source_commit` | `<sha>`, `<sha>-dirty` or `uncommitted` | `src/volbt/contract.py:117-122` | `app/src/lib/contract.ts:128-136` |

`manifest.json` lists the datasets. The app accepts a file only if its MAJOR version equals `SUPPORTED_MAJOR` (`contract.ts:16`) and ignores keys it does not know. Results datasets (M3 onward) will add `run`, `units` and `illustrative: false` blocks (ADR-0001 §5). After the review the `run` block also records `cap_mode` (ADR-0002) and `chain_mask` (ADR-0009), and `metrics` carries `n_trials` (N_raw), `n_trials_eff`, `dsr_raw` and `dsr_eff` (ADR-0010); all of these only add fields, so each is a MINOR bump.

**Why the app computes nothing** (ADR-0001 §6, and the rejected "let the app compute Sharpe" alternative): two implementations of one metric drift apart; the Python one is the tested one; and a reader must be able to trust that a chart shows the backtest's own number. The app may format, convert units for display, sort, filter and build *render-only geometry*. In M0 that last allowance is exactly `buildSurfaceGeometry` normalising IV into a unit box (`surfaceGeometry.ts:50`): it changes how the surface looks, not what any quoted number is.

- *Rejected:* a small API server (a process and CORS for batch artefacts that never change between runs), results baked into the JS bundle (no versioning, rebuild per run), parquet or DuckDB-WASM in the browser (moves computation into the app and breaks the 10 MB-per-file budget), and a shared TypeScript metrics library (the drift problem again).
- *Today the schema is executable in TypeScript only.* ADR-0001 §5 puts JSON Schemas in `volbt.export`, and the data-flow diagram schedules "Export + JSON Schema validation" with the M6 results (`docs/architecture/out/data_flow.mmd:43`); until then the parsers in `contract.ts` are the contract's executable form.

### 1.4 The illustrative SSVI hero, and why it is labelled

The app needs a believable surface to draw before M2 produces real ones. SSVI ("surface SVI", Gatheral and Jacquier 2014) gives a whole surface from a handful of numbers and has simple sufficient conditions for no static arbitrage. That is better than random noise, whose shape (flat in the wings, no skew, no steepening at short expiries) would teach the wrong picture. The maths is derived in `docs/concepts/01-ssvi-surface.md`.

Because it is made up, it is labelled **at four independent layers**, so no later edit can quietly present it as data:

1. The file carries `"illustrative": true` and a `label` (`tools/export_app_data.py:53-54`).
2. The TypeScript type is the literal `true` (`contract.ts:44`) and the parser *refuses* a surface that is not flagged (`contract.ts:188-189`).
3. The hero's badge text comes from a constant, not from the file (`SurfaceHero.tsx:187`, `content/about.ts:12`), so even a file with a changed `label` shows the warning.
4. The exporter refuses to write a surface whose parameters fail the no-arbitrage checks (`tools/export_app_data.py:48-50`). Be exact about how much that guarantees. It checks the two SSVI butterfly inequalities, which are sufficient conditions, on the expiries it is about to write; and it checks calendar arbitrage on the actual total-variance table, with the ATM term structure passed through to the check (an inverted one is refused: `test_refuses_to_export_an_inverted_term_structure`). Before the review fixes the calendar flag was computed from a hard-coded rising `theta`, so it could not be `False` and the guard could never trip on it. For `phi = eta/sqrt(theta)` the table check cannot disagree with "theta rises" (it is implied, see `docs/concepts/01-ssvi-surface.md` §5), so what the guard really adds over the old one is that changing the term structure can now be caught. It never looks at an option price or a density, so "well-formed" means "inside the sufficient conditions", nothing stronger.

The grid is 20 expiries (7 to 365 days) by 26 log-moneyness points (−0.30 to +0.20 in steps of 0.02); `illustrative_surface.json` is 9,317 bytes and `manifest.json` 362 bytes, against the 10 MB-per-file budget.

### 1.6 What the M0 adversarial reviews changed

Two adversarial reviews attacked milestone 0 before anything was committed. One went through the code and the app ([`00-code-ledger.md`](../validation/00-code-ledger.md)); the other went through the ten ADRs, the background note, the PR/FAQ and the diagrams ([`00-design-research-ledger.md`](../validation/00-design-research-ledger.md)). Five habits to take from this list:

1. **Say when each input became known.** The fill day's volume and the full-sample HAR fit both looked harmless and were not. (The fill day's *spread* is different: it survived review, because the fill price is meant to come from the fill day's own quote. Only its *volume* was look-ahead.)
2. **A claim that something is "conservative" needs a direction.** Check it for the long side and the short side separately.
3. **Test a guard with the mutant it is meant to stop.** The import test passed with `strategies → data` in it.
4. **An estimate is not a bound.** A number measured in a convenient setup describes that setup.
5. **Count what you tried and re-measure what you copy.** If you pick the best of N, N is part of the result; and a figure copied from a note without its unit or endpoints is how "12 rows" and "from 07-29 to 08-12" got into the ADRs.

On `TimeoutExpired` it calls `_kill_process_group` (`:44-50`), which sends SIGKILL to the whole group: `subprocess.run` would kill only git and leave a hung hook or daemon running, which the round-2 review found. A missing git (`FileNotFoundError`, `:72-73`) and a non-zero exit (`:74-75`) also return `None`. All failure routes return `None`; what `None` *means* is decided by the caller.
- `git_state()` (`:79-114`), three things matter:
  - `:84-86` `git rev-parse HEAD` fails in a repo with no commits (or outside a repo), which the next lines turn into `(None, False)`, meaning "nothing to point at, so nothing to be dirty relative to". `source_commit()` then prints `uncommitted` (`:121`; `tests/test_contract.py:63-66` and `tests/test_contract.py:94-103`). This repo is in that state today.
  - **Three questions, because each is a place a change can hide** (`:88-108`). The tree is clean only if all three ran and printed nothing.
    1. `:94-97` `git status --porcelain --untracked-files=no --ignore-submodules=none -- . ":(exclude)app/public/data"`: tracked files that differ from HEAD or the index. `--ignore-submodules=none` beats `diff.ignoreSubmodules=all`, which hid a modified submodule (`tests/test_contract.py:167-182`).
    2. `:101-104` `git ls-files -v`, keeping the entries tagged lowercase (`--assume-unchanged`) or `S` (`--skip-worktree`). Both make `git status` skip a file, so an edit to it reads as clean (`tests/test_contract.py:185-199`).
    3. `:108` `git ls-files --others --exclude-per-directory=.gitignore`: untracked files, hidden only by the repo's own committed `.gitignore` files. `.git/info/exclude`, `core.excludesFile` and `status.showUntrackedFiles=no` are per-machine, so a stamp must not depend on them (`tests/test_contract.py:158-164` and `tests/test_contract.py:202-220`), while the repo's own `.gitignore` is still honoured (`tests/test_contract.py:223-229`). A modified file and an untracked file count as dirty as before (`tests/test_contract.py:112-121`).
  - **It fails closed** (`:109-114`). Any of the three calls can fail while `rev-parse` succeeds (a truncated `.git/index` exits 128) or time out, and `_git` then returns `None`. The old `bool(None)` was `False`, so an unreadable tree was stamped clean. `:113-114` counts a `None` answer as dirty; only every call succeeding and printing nothing is clean. Tests: `tests/test_contract.py:137-155` (a truncated index, on a modified and on an unmodified tree), `tests/test_contract.py:275-281` (a real `fsmonitor` hook that blocks `git status` counts as dirty, and the patched 1 s timeout is honoured), `tests/test_contract.py:293-303` (after the timeout neither the hook nor its child is still running) and `tests/test_contract.py:319-332`, which spies on `Popen.communicate` and requires all four git calls to pass a timeout. A hung `rev-parse` gives `(None, False)`, i.e. `uncommitted`, which never claims a hash (`tests/test_contract.py:306-316`).
- **Why `app/public/data` is excluded** (`:28-31`, `:87`). The exporter stamps `source_commit` *first* (`tools/export_app_data.py:102`) and only then writes the files (`tools/export_app_data.py:108-109`). Those files live in the repo and carry a fresh `generated_at`, so a naive check would call the tree dirty *because of the previous export*. Two exports of identical code would then say `<sha>` and then `<sha>-dirty`. Excluding the folder makes the stamp a function of the code alone (`tests/test_contract.py:124-130`). The exclusion also means an edit to a committed JSON file by hand does not show as dirty, which is acceptable because that folder is generated (`tests/test_contract.py:232-243` pins this, including an `--assume-unchanged` file inside it).
- `build_envelope()` (`:125-137`): `now` is a parameter so tests can pin the clock (`:126`, `:130`). `:131-132` converts any timezone-aware time to UTC *before* formatting, so the trailing `Z` is true (`tests/test_contract.py:38-42`: 17:00 at UTC+5 prints `12:00:00Z`). `strftime` truncates, not rounds, so the stamp can be up to 1 s early (`tests/test_contract.py:45-52`). A naive `datetime` would be read as local time by `astimezone`; nothing tests that.
- **The hash must fit the app's pattern.** The app accepts `[0-9a-f]{7,64}`; git gives 40 hex digits (SHA-1) or 64 (a SHA-256 repository). `tests/test_contract.py:335-349` creates a repository of each kind and checks the length and the pattern. (The app side used to stop at 40; see §2.4.)

**`src/volbt/illustrative.py`: the SSVI surface** (maths in `docs/concepts/01-ssvi-surface.md` §3).
- `:31-45` constants. ATM vol runs 16% at 7 days to 20% at 365 (`:31-32`), `RHO = -0.7` (`:35`), `ETA = 1.0` (`:36`), the grid is 20 expiries and 26 strikes (`:39-40`), and `DAYS_PER_YEAR = 365` (`:41`), the same τ convention as ADR-0008 §5. `CALENDAR_CHECK_K` (`:45`) is the 201 log-moneyness points in [−1, 1] where the calendar check compares expiries: wider than the drawn [−0.30, 0.20] on purpose, since arbitrage hides in the wings.
- `sigma_atm` (`:48-51`): a straight line in DTE between `sigma_short` and `sigma_long`, which default to the 16% and 20% constants. They are parameters so a test (or a future caller) can feed in an inverted term structure; before, the line was hard-coded. `np.asarray(..., dtype=float)` lets one function take a scalar or an array.
- `atm_total_variance` (`:54-57`): `θ(T) = σ_atm² · T`.
- `phi` (`:60-62`): `φ(θ) = η/√θ`, split out so the formula, the checks and the Theorem 4.1 test all use one definition.
- `total_variance` (`:65-70`): `:67` takes φ·k and `:70` is the SSVI formula. At `k = 0` it collapses to `θ` for any ρ (comment, `:68-69`; `tests/test_illustrative.py:22-31`).
- `iv_grid` (`:73-85`), the numerically careful one:
  - `:76` rounds `k` to 10 decimals because `np.linspace` gives `-0.27999999999999997` where we mean `-0.28`; this makes `k = 0` land *exactly* on column 15 (`tests/test_illustrative.py:92-94`).
  - `:78` rounds the expiries to whole days (`7, 26, 45, 64, 82, 101, ...`), because the app labels them `30d`, not `30.4d`. The steps are therefore not exactly equal.
  - `:81-82` `[:, None]` turns expiries into *column* vectors, so numpy broadcasts them against the strike *row* into a `(20, 26)` table (`tests/test_illustrative.py:54-60`).
  - `:85` `np.sqrt(w / years)` is `σ = √(w/T)`. It returns `(k_grid, dte_grid, iv)`: the `k` axis comes first but `iv` is indexed `[dte][k]`. That mismatch is the classic transposition trap, which is why `tests/test_illustrative.py:85-87` pins shape `(20, 26)` (20 ≠ 26, so a transpose fails on shape alone).
- The no-arbitrage code is three functions now. `butterfly_conditions(theta, rho, eta)` (`:88-113`) is a pure function of its arrays: condition 1 is a strict `< 4` (`:111`), condition 2 is `<= 4` (`:112`), and both must hold at every expiry passed in. `calendar_condition(theta, w)` (`:116-126`) requires θ non-decreasing *and* the total-variance table non-decreasing down every column (`np.diff(w, axis=0) >= 0`): a longer-dated option may not be cheaper at *any* strike. `no_arbitrage_checks(dte, rho, eta, sigma_short, sigma_long, k)` (`:129-164`) builds θ from `dte` and the term structure, builds `w` over `CALENDAR_CHECK_K` (`:160`) and returns the three flags. Its docstring works out why, for `φ = η/√θ`, Gatheral and Jacquier's Theorem 4.1 reduces to "θ non-decreasing" (`∂θ(θφ) = φ/2`, always inside the bound), so the table is a direct check on the drawn numbers rather than extra detection power; and Remark 4.4 limits the butterfly guarantee to expiries up to some `t*₀` (`docs/concepts/01-ssvi-surface.md` §5). The `bool(...)` wrappers turn `numpy.bool_` into plain `bool`, so `all(checks.values())` and `is True` tests behave.

### 2.3 `tests/` (183 tests)

All Python tests state expected values as literals worked by hand, with the arithmetic in comments (`tests/test_illustrative.py:1-2`). Techniques worth copying:
- **Hand values and a reference point.** `tests/test_illustrative.py:34-51` (θ = 0.04: `w(-0.1) = 0.054928...`, `w(+0.1) = 0.027832...`), `:106-114` (one year), `:117-128` (7 days: IV 34.73% against 16% at the money).
- **Orientation is pinned twice.** `tests/test_export.py:110-115` checks that the *last* row (365 days) at column 10 (`k = -0.10`) is `0.234368`; with a transposed table it would be a different number.
- **Real git on a throwaway repo**, with identity passed per command so any machine works (`tests/test_contract.py:71-76`), and `GIT_CEILING_DIRECTORIES` (`tests/test_contract.py:102`) so git cannot wander up into *this* repo. The fail-closed tests then damage that repo on purpose: they truncate `.git/index`, set `status.showUntrackedFiles=no` and `diff.ignoreSubmodules=all`, mark a file `--assume-unchanged` or `--skip-worktree`, hide a new file in `.git/info/exclude` or a global `core.excludesFile` (each test first asserts that a plain `git status --porcelain` really hides the change, so it cannot pass for the wrong reason), and block `git status` with a real `core.fsmonitor` hook that starts a child process.
- **Strict JSON reading** rejects `NaN`, `Infinity` and also `1e999`, which is a *legal* JSON number that Python turns into `inf` and that the old `parse_constant` hook never saw (`tests/test_export.py:22-37`, plus `tests/test_export.py:137-143` to check the checker).
- **Committed file equals a fresh export, byte for byte.** `assert_matches_a_fresh_export` (`tests/test_export.py:245-256`) re-exports with the committed manifest's own `generated_at` and `source_commit`, so after that any difference in bytes (a value, key order, indentation, a CRLF line ending) is drift: "changed the model, forgot to re-run the exporter" fails. It used to compare parsed numbers to 2e-6, which cannot see layout changes. The comparison is itself tested on a damaged copy: a one-digit change and a CRLF conversion both fail it (`tests/test_export.py:283-289`, `tests/test_export.py:292-297`).

### 2.4 `app/src/`

**`src/lib/contract.ts`: how it validates.** Everything fetched is untrusted until it passes a parser (`:4-7`). Each parser takes `unknown`, returns a typed value or throws a `ContractError` naming the exact field (`:18-23`, `:63-65`).
- **The major-version rule** (`:11-13`, `:87-96`). `SEMVER` (`:85`) accepts only `MAJOR.MINOR.PATCH` with no leading zeros, so `0.1`, `v0.1.0`, `01.0.0` and `0.1.00` fail (SemVer forbids leading zeros; "0.1.00" would otherwise name the same version as "0.1.0" under a different string). Then `:91-93` compares the major to `SUPPORTED_MAJOR = 0` (`:16`) and nothing else, so a MINOR or PATCH bump that only adds fields is accepted. Unknown keys are dropped because each parser *rebuilds* its result from the validated pieces (`:179`, `:213`). Note this is looser than strict semver, where major 0 means "anything may change".
- **Ragged grids** (`:198-209`). `iv` must be an array with exactly `dte.length` rows (`:200`) and every row exactly `moneyness.length` long (`:204`). A ragged table would otherwise surface much later as `undefined` positions, hence `NaN` vertices.
- **Non-finite values** (`:141-150`, `:205-207`). Both axes and every cell go through `typeof x !== 'number' || !Number.isFinite(x)`. `null` (what some serialisers write for `NaN`) fails the `typeof`; `1e999` is a *valid JSON literal* that `JSON.parse` turns into `Infinity` (checked in Node this session), and fails `isFinite`. A bare `NaN` never gets here: `JSON.parse` throws and `getJson` (`app/src/data/loadAppData.ts:53-57`) reports "not valid JSON".
- **Other guards.** Axes need at least 2 values (`:145`) and must be strictly increasing; the test is `!(xs[i] > xs[i-1])` (`:154`), so `NaN` and ties fail too. `dte[0]` must be positive (`:196`). IV must lie in `(0, MAX_IV]` with `MAX_IV = 5` (`:59`, `:207`), which catches an exporter that wrote percent (18) instead of a decimal (0.18). `illustrative` must be exactly `true` (`:188-189`). Manifest names must be unique (`:173-174`). Manifest paths must match `SAFE_RELATIVE_PATH` (`:139`, `:176`), which rejects a leading `/`, `..`, a scheme, a backslash or a query, because the loader pastes the path into a URL (`app/src/data/loadAppData.ts:78`).
- **Impossible dates are rejected.** `Date.parse` is not a calendar: V8 reads `2026-02-30T00:00:00Z` as 2 March and hour 24 as midnight of the next day (checked in Node this session), so the old check accepted both. `isRealTimestamp` (`:108-116`) also builds the wall-clock part as a UTC date and requires that printing it gives back the same characters, so a rolled-over date fails; it bounds the offset itself (hours up to 23, minutes up to 59) instead of trusting the engine. Leap days still pass (`2024-02-29`). Tests: the "Well-formed but not real" group in `contract.test.ts:128-139`.
- **`source_commit` fits SHA-256 repositories.** `SOURCE_COMMIT` (`:128`) takes 7 to 64 hex digits (it stopped at 40, which refuses the 64 digits a SHA-256 git repository writes); the Python side produces 40 or 64 (§2.1).
- **The manifest and the file must agree.** `assertDatasetMatchesEntry` (`:228-235`) compares the `schema_version` the manifest lists for a dataset with the one the file says about itself, and `loadAppData` runs it after both parsers pass (`app/src/data/loadAppData.ts:81`). A manifest from one export run and a data file from another is therefore refused as a `contract` failure instead of rendering.
- **The real files are tested too.** Every other contract test feeds the parsers hand-made fixtures, so a change on the Python side could break the app unseen. `src/test/contract.e2e.test.ts` (`src/test/contract.e2e.test.ts:40`) reads the committed `app/public/data/*.json` and runs the real parsers and the real loader over them. It uses `import.meta.glob(..., { query: '?raw' })` rather than Node's `fs`, because the app's `tsconfig` has no Node typings. A damaged copy (wrong major, renamed key, mismatched version, a non-hash `source_commit`) fails it.
- **`commitState`** (`:240-243`) maps the string to `clean`, `dirty` or `uncommitted`; the About page shows a badge unless it is clean (`views/AboutPage.tsx:30`, `:41-43`).

**`src/lib/surfaceGeometry.ts`: from `iv[i_dte][j_k]` to vertices and indices.** Free of three.js on purpose (`:1-4`): it returns plain `Float32Array` and `Uint32Array`, so the whole mapping is unit-tested without a GPU.
- *Preconditions* (`:55-61`): at least 2 × 2, `iv` has `nT` rows each `nK` long. The parser already checked this; the function checks again because it is pure and reusable (defence in depth).
- *Extents* (`:34-43`, `:63-68`): min and max of each axis; a non-finite value throws `RangeError`. `unit` (`:46-48`) maps `[lo, hi]` to `[0, 1]` and sends a degenerate axis (`hi === lo`) to 0 instead of dividing by zero.
- *Vertices, row-major* (`:73-85`). `i` walks the `dte` rows and `j` the `moneyness` columns, so vertex `(i, j)` has index `v = i * nK + j` (`:75`). Position is `x = unit(moneyness[j])`, `y = unit(iv[i][j])` (up), `z = unit(dte[i])` (`:76-79`); colour is the ramp at `y` (`:80-83`). Worked example on the real 20 × 26 grid: `iv[19][10]` (365 days, `k = -0.10`) is vertex `19 * 26 + 10 = 504`, at `(0.4, 0.2654, 1)` because the IV range is `[0.115782, 0.562677]` (measured this session). Float32 stores `x` as `0.4000000059604645`, which is why the tests compare with `toBeCloseTo` (`surfaceGeometry.test.ts:4-7`).
- *Triangles and winding* (`:87-101`). Each grid cell has corners `a = (i, j)`, `b = (i, j+1)`, `c = (i+1, j)`, `d = (i+1, j+1)` (`:94-97`) and becomes two triangles `(a, c, b)` and `(b, c, d)` (`:98`). Seen from above (+y) with x to the right and z toward the viewer, `a, c, b` goes top-left, bottom-left, top-right: counter-clockwise, so the *top* of the surface is the front face. `surfaceGeometry.test.ts:84-93` checks every triangle's normal has positive y. (In `app/src/views/SurfaceHero.tsx:49` the material is `DoubleSide` and unlit, so a wrong winding would not even show; it would bite the day someone adds lighting or back-face culling.)
- *Counts* for 20 × 26: 520 vertices, 475 cells, 950 triangles = 2,850 indices (`:90` allocates `6 * (nT-1) * (nK-1)`), and 994 wireframe segments = 1,988 indices (`:104`), each vertex adding one segment to its right and one below (`:106-117`). All measured this session.
- `axisLabels` (`:133-153`) anchors nine labels just outside the unit box around the viewing corner `(x=1, y=0, z=1)`.

**The daily loop** is the heart of M3. Its order is fixed by ADR-0001 and drawn in [`engine_daily_loop_sequence.mmd`](../architecture/out/engine_daily_loop_sequence.mmd) and on the app's Architecture page:

1. load the snapshot for *t* and open a `MarketView` at `as_of = t`;
2. start-of-day events: assignments decided at *t−1*, dividends with ex-date *t*, cash interest; then any pending order on a lot those events removed is cancelled (`LOT_REMOVED`), so it is never filled against a contract no longer held;
3. fill the orders created at *t−1* against the *t* quotes, in integer cents and under the hard cap of 100 contracts a line (ADR-0002);
4. settle contracts that expire at *t* (ADR-0003);
5. mark every lot and compute greeks (ADR-0004);
6. delta-hedge at the *t* close (ADR-0005);
7. portfolio greeks snapshot and P&L attribution;
8. end-of-day greek and stress budgets and the net margin requirement; reductions become orders for *t+1* (ADR-0006, 0007);
9. compute signals from the `MarketView`, then the strategies decide; pre-trade risk check (greeks, stress cells, net margin); orders queued for *t+1*;
10. early-exercise and assignment decisions for *t+1*: calls by a closed form before an ex-date, puts on a CRR lattice (ADR-0003 §5);
11. write the ledger.

The point of the order: yesterday's orders fill at today's close, so fills precede marks and every new lot is marked on the day it is filled; today's orders fill tomorrow.

## 4. What the data inspection found

All of the following was measured read-only on 2026-10-28 on the local copy of Kaggle `dudesurfin/spy-options-eod-volatility-surface-2010-2023` (OptionsDX) and the DoltHub `post-no-preference/options` clone, and written up in ADR-0001, 0002, 0004, 0008 and 0009. The raw files were not modified.

> ### Guess first (ungraded)
>
> Write your guesses down (a number, or a direction and a reason) *before* reading the findings below. They are not graded: the point is to find out where your intuition about options data is wrong.
>
> 1. The OptionsDX file has one wide row per (date, expiry, strike). **How many rows do you expect per snapshot date in 2010, and how many in 2021?** What makes the count grow, and by roughly how much?
> 2. **At what time of day are the option quotes and `UNDERLYING_LAST` stamped?** If a strategy computes its signal from this snapshot, what is the earliest price it can trade at without look-ahead?
> 3. Each row carries the vendor's own implied vol, call and put. **Would you trust it to mark your book? At the same strike and expiry, should the call IV and the put IV agree? If they do not, name two reasons.**
> 4. **What share of call quotes do you expect to have `bid = 0`? What does a null daily volume mean: zero traded, or unknown?** Would you expect total chain volume to trend smoothly from 2010 to 2023, and what would you check before believing a jump?
> 5. A short-straddle strategy sells when IV looks rich against a forecast of realised vol. **What happens to its backtested P&L if orders fill at the same close that produced the signal?** Which way is the bias, and why?
> 6. DoltHub lists only about 17 to 27 strikes per expiry, on a grid about 2.2% of spot apart, and re-centres them every day. **What happens to the quote of a contract you bought last week, when you want to sell it today?**

### 4.1 The OptionsDX files

- **Size and shape.** 14 yearly parquet files, about 569 MiB; the original brief's "~509 MB" was wrong. 9,468,584 rows over 3,508 snapshot dates, 2010-01-04 to 2023-12-29. There are 33 columns and the names really do contain square brackets. The natural key (date, expiry, strike) is unique on all rows. A script running nine full-scan DuckDB aggregates over all 14 files took 1.3 s wall-clock, which is why one machine and no server are enough.
- **Q1: rows per date.** About 1,052 rows a date in 2010 and 5,070 in 2021. Average expiries per date grew from 14.6 (2010) to 35.7 (2020) and average strikes per date from 133 to 327 (2022): more expiries listed at once and a finer strike grid. Expiration-day (0-DTE) contracts appear on 38 dates in 2010, 166 in 2022 and all 250 dates in 2023. A strategy and a performance number from 2010 are therefore built on a much thinner chain than one from 2021.
- **Q2: the timestamp.** `QUOTE_TIME_HOURS` is 16.0 on every row; `QUOTE_UNIXTIME` and `EXPIRE_UNIX` convert to 16:00 America/New_York on 3,507 of the 3,508 dates (2010-07-09 reads 16:00:01, one second late), and each date has one `UNDERLYING_LAST`. So the quotes and the underlying share the 4 pm stamp, the SPY close. SPY options trade until 4:15 pm ET, expiring ones included (SEC Rel. 34-105153), so a trader could compute a signal from the 4:00 snapshot and still trade, but *not at the 4:00 quotes*. That is the root of ADR-0002's *t+1* rule.
- **Q4: bad quotes.** `bid = 0` on 745,993 call rows (7.9%) and 632,224 put rows; crossed (`bid > ask`) on 9,435 calls and 24,046 puts; 96,009 locked calls (`bid = ask > 0`); null bid or ask on 11,721 calls; null vendor IV on 588,461 calls and 472,386 puts. In 2019, puts with `K/S < 0.80` had `bid = 0` on 22.1% of rows, against 0.6% at `K/S ≥ 0.97`. Hence "flag, do not drop": a held contract with a zero bid still needs a mark.
- **Q4: volume.** Unreliable before 2021. The median daily total chain volume jumps from 366,024 contracts in Dec-2020 to 2,981,034 in Jan-2021, about 8 times, with no market event behind it. `[C_VOLUME]` is null on 37.6% of rows overall and on 84-97% of near-ATM 20-40 DTE rows in 2010-2012. The break is a single step at the yearly-file boundary (371,587 contracts on 2020-12-31, 3,417,626 on 2021-01-04). The 2021-01-15 370 put has null volume every day from 15 to 31 Dec 2020 and then 9,775 to 58,087 contracts a day from 4 to 8 January (11,123, 9,775, 32,828, 45,526, 58,087; checked in the data this session): null means *unknown*, not zero. There is no open interest. A volume cap that read null as zero would block almost every ATM trade in 2010-2012 because of an artefact; rescaling pre-2021 volume by 8 would fabricate data. Volume also depends on the expiry type: in 2021-23 the median near-ATM volume was 68 contracts a day on weeklies and 1,525 on monthlies. ADR-0002 §5 therefore makes a hard cap of 100 contracts a line the rule of record in every split, trades standard monthly expiries by default, and runs the 10% volume cap, on the volume of the *order* date and only where volume is reliable, as a 2021-23 diagnostic that reports a capacity haircut.
- **Spreads.** For near-ATM calls (`abs(K/S - 1) < 1%`) with 20-40 DTE the median quoted spread is $0.02 to $0.08 depending on the year, 0.4 to 2.5% of mid. In Mar-2020 the same median widened from $0.245 (9 Mar) to $0.61 (16 Mar), which is why a fixed basis-point cost would miss exactly the days a short-vol book is losing.
- **Q3: vendor IV and greeks.** On 2023-06-15, 29 DTE, strike 443: call mid 5.560 with vendor `C_IV` 0.12062, put mid 6.315 with vendor `P_IV` 0.11490. One strike carries two IVs 0.57 vol points apart. No standard input reprices the call at the vendor's IV (r = q = 0 gives 5.813; r = 5.25% with q = 1.5% gives 6.465). A forward implied from put-call parity over the 438-448 strikes (442.00 to 442.36, against S = 442.61) shrinks the gap but does not remove it: the IV solved from the call mid on that forward is 0.1196. The next day, 2023-06-16, was an ex-dividend date ($1.638367). So the two reasons are the *forward* (the dividend and rate the vendor assumed) and the *American exercise premium*, which differs between calls and puts. The premium still biases the parity forward low: on that date the raw `F_K` falls from 442.376 (K = 436) to 441.871 (K = 450), almost monotonically (two small upticks, at K = 439 and 441), and the median parity forward, about 442.24, sits about 12 bp below the carry forward implied by DGS3MO and the dividend (442.80), of which the premium explains only about 4 bp and the rest is unexplained. ADR-0008 fixes the forward first, then removes the premium with a CRR lattice (de-Americanisation, §3a). Vendor theta (−0.0914 a day) does not reconcile with Black-Scholes-Merton on calendar days (−0.104 to −0.126), while vendor gamma and vega match to within 1%.
- **Day count.** Vendor `[DTE]` is fractional (x.04 or x.96) on 3,267,818 rows although both timestamps are 16:00 ET every day: the fraction is a one-hour daylight-saving shift, not real time. ADR-0008 §5 counts calendar dates instead.
- **Calendar anomalies.** 12 snapshot *dates* fall on market closures and hold 44,926 rows (including 2012-10-29 and 10-30, Hurricane Sandy, 1,416 rows each, both with the same stale `UNDERLYING_LAST` although only 6.6% of their quotes are identical; 2018-12-05; and nine dates in 2022). They look like late re-snapshots, not copies: at most 2.6% of their quotes match a neighbouring session's, and the underlying differs by cents (about 4 cents on 2022-07-04 against 07-01), so the vendor's normal-day `UNDERLYING_LAST` may not be exactly the official close either. 26 weekday sessions have no snapshot (for example 2011-01-19 to 2011-01-25, five sessions). The 2022-06-20 row (a Juneteenth closure) shows an underlying that we *believe* is the 2022-06-17 close, so 06-17 looks mislabelled: this is unverified until yfinance closes are loaded. Hence ADR-0009 builds the calendar from SPY's own bars.

### 4.2 The DoltHub clone (out of sample)

- **Q6: it disappears.** Each expiry has a median of 17 to 27 strikes on a grid about 2.2 to 2.3% of spot apart, *re-centred every day*, and an expiry first listed at 25 DTE or more is listed on only about half the sessions between its first and last listing. The 2025-04-30 520 put, for instance, was quoted on only 2 of the 14 sessions between 2025-03-31 and 2025-04-17 (04-02 and 04-14). A held contract is usually not quoted on later days, so a quote-level engine would end almost every exit as `NO_QUOTE`; ADR-0009 §4 runs DoltHub in `surface` mode instead and *estimates* the distortion that causes (an estimate, not a bound) by running OptionsDX in `surface` mode on a chain masked by DoltHub's own SPY sampling of the same 2020-23 dates, reported separately for 2020-22 and 2023 because DoltHub's expiry persistence differs between them (median listing share 0.286 in 2020-22, 0.50-0.54 from 2023), with 2023 the closest analogue of the holdout. A surface run on the full, dense OptionsDX chain would measure only the small in-grid error (median 0.04 vol points); the errors that matter are marks across expiries (0.24), beyond the last strike (0.19 with the Lee-clipped extrapolation, against 0.67 flat) and below the front expiry (1.21, at every 7-DTE exit).
- **What it lacks.** The `option_chain` table (13 columns) has no volume, no sizes, no last price, no underlying price and no snapshot time. So there is no volume cap beyond the hard 100, the snapshot time must be inferred from the cross-vendor check, and the underlying must come from yfinance.
- **Coverage.** 1,299 SPY dates, 2019-02-09 to 2026-10-26 (46 of the 48 dates in 2019 are Saturdays). 76 to 266 rows per date in 2024 (86 to 210 in 2025, 162 to 216 in 2026); 3 expiries in 2020-24, 3 to 4 in 2025 and 4 in 2026, at median DTEs of about 13-14, 29 and 51-56; the front expiry is 10 to 18 DTE, so **nothing under 10 DTE is ever listed**; only 8% of the expiries listed in 2024-26 are third Fridays. Monday, Wednesday and Friday only until Aug-2024 (with a handful of Tue/Thu dates), some Tue/Thu dates in Sep-2024, and **almost every weekday only from Oct-2024 (11 sessions between 2024-10-01 and 2026-10-26 have no SPY rows)**. There are rows on market closures (2020-01-20, 2024-01-01, 2024-09-02).
- **The gap.** There are **no SPY dates from 2024-07-30 to 2024-08-09**. 2024-07-29 (110 rows) and 2024-08-12 (116 rows) both exist, but the Monday/Wednesday/Friday sessions 07-31, 08-02, 08-05, 08-07 and 08-09 are missing, so the Aug-2024 vol spike (VIX 38.57 on 5 Aug) cannot be replayed. A run passes through the hole on `STALE_SURFACE` marks, and ADR-0010 reports the window as `NO_DATA` and covers it only through the stress grid cells (−10%, +20 points) and (−5%, +10). Apr-2025 is covered: none of its sessions is missing. The hub's own status file says SPY rows begin 2019-02-09 (a Saturday); the revised ADR-0009 measured it.

### 4.3 Q5: why same-close fills flatter a short straddle

This one is reasoning, not measurement (ADR-0002 §1 and its rejected alternatives). If the order fills at the snapshot that produced the signal, the signal and the fill share the same quote noise. Take a **spuriously high bid**, or a mid it has pushed up. It raises the mid-based IV, which is what makes "IV is rich" fire, and the seller then fills at that same snapshot at `mid − k·half-spread` (ADR-0002 §2), which is the *bid* at the default `k = 1`. So the inflated number is exactly the price received. The bias is *favourable*: it books the noise as edge. A spuriously high *ask* is the wrong example for a seller: it would raise the mid and so the signal, but a seller never fills at the ask, so at `k = 1` the fill price would not move (the ask is a buyer's cost). You only see the 4:00 pm snapshot once it is stamped, so you cannot trade at its quotes. ADR-0002 keeps `fill_timing = same_close` only as a diagnostic, and reports the gap between the two modes as the "same-snapshot premium".

## 5. Pitfalls this design guards against

Except for the last row, everything below is specified in the ADRs and built from M1 onward; M0 builds only the guards in the last row.

| Pitfall | How the design guards it | ADR |
|---|---|---|
| **Look-ahead**: a strategy or a signal sees data after *t* | Strategies and signals get a `MarketView` fixed at `as_of = t`; neither may import `data`, which an AST test will enforce on each module's explicit allow-list (`strategies → data` is a required mutant; the test is specified and implemented from M1, not built in M0); any later read raises `LookAheadError`, and a view past the run's split end raises `SplitError`; signals are computed causally from the view with monthly refits, and a perturb-the-future test checks the state the guard cannot see (a full-sample HAR forecast moved from 2.985e-03 to 2.992e-03 when only later data changed); a signal from *t* fills at *t+1*; a test requests the 03-15 chain from a 03-14 view and must see the error | 0001 §2, §4, tests 1, 2, 6; 0002 §1 |
| **Fills at mid** | Fill at `mid ± k·half-spread`, `k = 1` by default, tick-rounded against you, with a sweep over `{0, 0.5, 1}`; `k = 0` is labelled a known-optimistic bound. Paying bid/ask instead of mid cut monthly short-put returns by 4-6.9% in Santa-Clara and Saretto | 0002 §2 |
| **Same-close fills** share quote noise with the signal | Orders wait for the next snapshot; unfilled quantity is cancelled, not carried | 0002 §1, §6 |
| **Null volume is not zero**, and tomorrow's volume is not known today | A hard cap of 100 contracts a line is the rule of record in every split (DoltHub has no volume, and one rule must hold across splits); the 10% volume cap uses the contract's volume on the *order* date, never the fill day's, applies only when `source = optionsdx`, date ≥ 2021-01-04 and volume is not null, and is a diagnostic that reports a capacity haircut; reduce-only orders are never volume-capped; the quality flag `VOLUME_UNRELIABLE` (bit 9) marks the rows | 0002 §5; 0009 §3; 0010 §1 |
| **Stale marks** hide risk: NAV looks smooth when quotes fail | One mark per lot per day by a fixed rule order, with `mark_source` recorded; never carry a price forward (carry the *IV* at the same moneyness instead); report `NAV_mid` and `NAV_liq`; flag a day `DEGRADED` above 20% model-marked | 0004 |
| **Vendor IV and greeks are inconsistent** | Recompute IV from OTM mids on a parity forward with Black-76, after a CRR lattice removes the American early-exercise premium from the quotes (left in, it biased the forward 4-7 bp low at 5% rates); greeks always from our model | 0008 §1-3, §3a, §7; 0004 |
| **Dividends counted twice, or not at all** | The forward carries the dividend, so pricing never needs `q`; dividends enter only as cash on ex-dates for share positions, in the early-exercise test and in the forward fallback | 0008 §4; 0005 §6 |
| **American early exercise** is ignored, or modelled one-sidedly | Calls are assigned before an ex-date when `D > P_E(K) + K(1 - e^(-rτ))`, which is exact for the last ex-date before expiry; puts are decided on a CRR lattice and assigned when continuation value − intrinsic ≤ $0.005, because the old inequality `K(1 - e^(-rτ)) > C(K) + PV(dividends)` is only necessary, not sufficient, and fired 3-5 points of moneyness too early; every qualifying short is assigned (an explicit worst case); the default DTE ≤ 7 exit avoids most of it | 0003 §5 |
| **Physical delivery and pin risk** at expiry | Settlement at the 4 pm close, ±100 shares at *K*; a hedged book nets delivered shares against its hedge; an unhedged book liquidates at *t+1*; a pin flag within $0.50 | 0003 §2-4 |
| **Capital base and margin**: the "return" has no denominator | Fixed $1M, NAV-based returns; Cboe margin recomputed daily; a margin call compares the **net** requirement (gross minus the short options' market value, which NAV already subtracts) with NAV and forces liquidation at *t+1*. Margin calls alone turned a +2.7% a month portfolio containing a short near-maturity 5% strangle into −1.0% a month in Santa-Clara and Saretto | 0007 |
| **Unit confusion** ("vega 2,500") | Gamma per 1%, vega per vol point, theta per calendar day, all portfolio USD, from our Black-76 | 0006 |
| **Greek budgets that do not bound the loss** | A binding full-revaluation stress budget: loss ≤ 15% of NAV at (−10%, +20 vol) and ≤ 35% at the worst of the 63 grid cells, checked pre-trade and at end of day. Without it a margin-capped book of 10%-OTM strangles passed every greek budget and lost 18.8% of NAV at (−10%, +20) and 58.3% at (−20%, +40) | 0006 |
| **Multiple testing**: the best of N trials is biased up | Every `config_hash` is a logged trial; PSR and DSR use N_eff (trials clustered at ρ* = 0.5) and N_raw (trials plus logged design choices), and the headline DSR is the lower of the two; fixed splits chosen before any strategy ran; at most two validation re-runs per frozen config, each a trial; the holdout is run once and labelled semi-blind | 0010 §1-2 |
| **A drawdown mistaken for a vol shock** | Regimes by VIX level, term structure and vol shock; 2022 reported as a drawdown-without-shock contrast | 0010 §3-4 |
| **Calendar and day-count errors** | Calendar from SPY bars, closures flagged, calendar-date τ across daylight saving | 0009 §1; 0008 §5 |
| **Non-reproducible output** | No wall clock in the engine, seeded randomness, sorted iteration, rounding per unit at export, exact pins, input fingerprint | 0001 §7 |
| **M0-specific:** placeholder data shown as real, a stale notebook, an export stamped with the wrong commit | Four-layer labelling (§1.4); the byte-level sync test (`tests/test_notebooks.py:20-28`); the dirty check that ignores the generated folder (`src/volbt/contract.py:87`) and fails closed when git cannot answer | 0001 §5 |

## 6. Explain it back: interview questions

Answer aloud first, then check against the code and ADRs. They get harder as they go. They are graded in the session.

1. **Architecture.** Why is the engine event-driven with a daily step instead of a vectorised signal-times-position backtest? Name three pieces of state the loop carries from one day to the next that a `cumsum` cannot express. Then: ADR-0001's step order differs from the original brief's. What changed, and which concrete bug would the brief's order produce for a lot opened by yesterday's order?
2. **The contract.** Python writes `moneyness`, `dte` and `iv[i_dte][j_k]`. Walk the file from `iv_grid()` to a vertex on screen: where could a transposed grid be caught, and by which tests and lines? Then: a colleague adds a field `sharpe_ci` to a future `metrics.json`. What version bump is needed, what does an old build of the app do, and what change would force a MAJOR bump? Why does the exporter set `allow_nan=False` when the app also checks `Number.isFinite`?
3. **`source_commit`.** What are the three values `source_commit` can take, and how does `git_state` produce each? Why is `app/public/data` excluded from the dirty check, and what concrete failure would you see in two consecutive exports if it were not? What happens if `git status` itself fails (a corrupt index) or the repository's config hides untracked files, and why does the answer have to be "dirty"? What does the check still miss?
4. **The gamma-rent formula.** Derive `δΠ ≈ ½ΓS²[(δS/S)² − σᵢ²δt] + 𝒱δσᵢ` for a delta-hedged long option from the Taylor expansion, saying where the Black-Scholes PDE is used and what theta is paying for. For a short ATM straddle at σᵢ = 20%, what is the break-even daily move? Why is weekly hedging about √5 times noisier than daily, and why is the number in our simulation 2.1 rather than 2.24?
5. **Fill timing.** Why can a signal computed from the 4:00 snapshot on day *t* not be filled at the *t* quotes, even though SPY options trade until 4:15? What is the "same-snapshot premium", and how would the engine measure it (which mode, and where is that mode recorded in the output)? Why does the hedge get the one exception to the *t+1* rule, what does that choice assume about execution, and what does the `next_open` variant change?
6. **Early exercise.** Starting from put-call parity after the ex-date, derive the call exercise condition `D > P(K) + K(1 − e^(−rτ))` and explain what the interest term does that the "put < dividend" heuristic misses. Then take ADR-0003's tests 5 and 6 and say, with the numbers, why the same short 440 call is assigned at τ = 0 (the ex-date is also the expiry) and not at τ = 30/365. Why is the old put inequality `K(1 − e^(−rτ)) > C(K) + PV(dividends)` necessary but not sufficient, what does the CRR lattice add, and why did the old rule's error matter little in 2010-2015 but a lot at 2023's rates? In which direction does a false early assignment move a short put's P&L, and why was the M0 text's "more assignments is conservative" wrong? Why is "assign every qualifying short" an explicit worst case for calls rather than a modelling flaw?
7. **Greek units.** For one long call with S = F = K = 400, σ = 0.20, τ = 30/365, r = 0, state `delta_usd`, `gamma_1pct_usd`, `vega_1vol_usd` and `theta_1d_usd` in ADR-0006's units and what each means. Use `gamma_1pct_usd` to give the P&L of a 2% move without recomputing. Why does `gamma_1pct / vega_1vol = 1/(σ·τ)` decide whether a short position is gamma-limited or vega-limited, and at what tenor do the two per-position limits bind together at σ = 20%? Then: why did the greek budgets alone fail to bound the loss of a margin-capped book of 10%-OTM strangles, and what does the stress budget limit instead?
8. **Capital base, and whether a result is real.** A strategy shows Sharpe 1.9 on return-on-margin after 40 configurations were tried. Using ADR-0007 and ADR-0010: what denominator would you insist on and why, and does scaling the leverage of a constant-leverage book change a Sharpe on excess returns (what does leverage change instead)? What do you compute from the trial log to decide whether 1.9 survives selection (state the PSR and DSR formulas, what N and V[SR] are, how N_eff and N_raw differ and which DSR is the headline)? Which split could each configuration be tuned on, why can the holdout be run only once, and why is it only *semi-blind*? Finally, compute ADR-0007's short-straddle margin by hand at S = 420, and again after a crash to S = 300, and say what that does to forced liquidation on the net basis, and why the gross figure the M0 rule compared with NAV would have called margin too early.

## 7. What's next (milestone 1): the option-chain data layer and quality filters

The deliverable is `volbt.data` and the first real tables, built to ADR-0009 and the M1 part of [`data_flow.mmd`](../architecture/out/data_flow.mmd):

- **Loaders** for OptionsDX parquet (asserting the exact 33 names and types against a 20-row fixture), DoltHub (13 columns; opened *read-only*, with `dolt status` run before and after and required to be clean; since 2026-10-29 in this project's private mirror of the clone, never in the shared clone itself, see [concept 06](../concepts/06-private-dolt-mirror.md)), yfinance (SPY daily OHLC unadjusted, `auto_adjust=False`; the library's default adjustment behaviour must be verified), FRED `DGS3MO` and the Cboe VIX history. Raw files land under `$VOL_DATA_DIR/vol-strategy-backtester/raw/`. As of M1 (default taken 2026-10-29), downloads and built tables live in the repo's git-ignored `data/` folder (`volbt.config.work_dir()`).
- **The trading calendar** from SPY bars, with the relabel rule (move a closure-dated row to the nearest earlier session with no snapshot only when `UNDERLYING_LAST` is within $0.02 of that session's SPY close) and the `NON_SESSION_DATE` and `RELABELLED` flags. This is also where the unverified 2022-06-20 mislabel gets checked, and where the 12 closure-dated snapshot dates (44,926 rows) are relabelled or dropped.
- **The DoltHub sampling mask** (`chain_mask = dolthub`, ADR-0009 §4): on each date, only the OptionsDX (expiry, strike) pairs DoltHub lists for SPY, so that the surface-gap runs replay DoltHub's own sampling.
- **`option_quotes`**: one long row per (`source`, `quote_date`, `osi_symbol`), with the 13-bit `quality_flags` mask (the IV-related flags arrive in M2) and the quality report, whose counts per flag feed the **quality gate**.
- **The cross-vendor check** on the 2020-01-06 → 2023-12-29 overlap, DoltHub's Monday/Wednesday/Friday dates (30-day ATM IV from each vendor; DoltHub's parity-implied spot against the SPY close). There is no same-date overlap in 2019, because 46 of DoltHub's 48 SPY dates that year are Saturdays; they are compared with the preceding Friday only as a labelled test of the hypothesis that they are Friday closes. It tells us DoltHub's effective snapshot time, and the tolerances are *set in M1 after we have looked at the distribution*. Also checked: whether VIX3M is available for the term-structure regime.
- **Tests** to write first: schema pin, calendar fixture, one fixture row per flag with the exact bits, `STALE` at +1% vs +0.25%, OSI symbol round trip, and the DoltHub read-only SQL guard (ADR-0009 §How we will test it).
- **Open items carried in:** the illustrative surface used to say it would be "replaced in milestone 1" (the docstring of `src/volbt/illustrative.py` and the notebook text), but ADR-0001's dataset table puts the real `surface_frames` in M2 (it needs forwards, IV and smiles). Both now say M2, the pricing core (`src/volbt/illustrative.py:4-6`, `tools/build_notebooks.py:214-215`), and M1 only loads and cleans the data, so M1 itself does not replace the hero.

The M1 walkthrough will open with its own predict-first block, so make a habit of writing guesses down (for example, what share of the 2010-2012 chain you expect to survive a zero-bid filter) before the first quality report is run.
